# AI 深度审查指南

本文档详细说明 AI 如何进行标准草稿的深度审查。

## AI 审查原则

### 1. 语义理解优先

AI 应基于对内容的语义理解进行判断，而不仅仅是规则匹配。

### 2. 上下文分析

AI 应考虑内容在特定上下文中的合理性，避免孤立判断。

### 3. 灵活判断

AI 应能处理边界情况、特殊情况，提供合理的判断和建议。

### 4. 专业建议

AI 应提供基于 GB/T 1.1-2020 标准的专业修改建议。

## AI 审查流程

### 步骤1：读取文档内容

**操作**：
```
使用 read_file 工具读取 .docx 文件
提取文档结构和内容
```

**提取信息**：
- 文档标题
- 章节结构（前言、范围、术语和定义等）
- 段落内容
- 图表信息
- 引用信息

### 步骤2：执行脚本检查

**操作**：
```
运行 check_standard.py 脚本
获取格式、规则层面的问题
```

**脚本输出**：
- JSON 格式的检查结果
- 问题列表（位置、描述、建议）

### 步骤3：AI深度审查

根据脚本检查结果和文档内容，进行AI深度分析。

#### 3.1 前言内容审查

**审查内容**：

1. **标准编制依据**
   - 检查是否包含"按照 GB/T 1.1-2020"等表述
   - 判断表述是否规范

2. **提出单位和归口单位**
   - 检查是否说明提出单位
   - 检查是否说明归口单位和技术委员会
   - 格式示例："本文件由XXX提出。本文件由XXX技术委员会（TC/XXX）归口。"

3. **起草单位和起草人**
   - 检查是否列出起草单位
   - 检查是否列出主要起草人
   - 格式示例："本文件起草单位：XXX、XXX。本文件主要起草人：XXX、XXX。"

4. **附录说明**
   - 如有附录，检查是否说明附录性质
   - 格式示例："本文件的附录A是规范性附录，附录B是资料性附录。"

5. **与其他标准的关系**
   - 如替代旧标准，检查是否说明
   - 格式示例："本文件代替XXX-XXXX。"

**AI判断逻辑**：

```
读取前言章节内容

分析是否包含：
- 编制依据：搜索"按照"、"GB/T 1.1"等关键词
- 提出单位：搜索"提出"、"归口"等关键词
- 起草信息：搜索"起草单位"、"起草人"等关键词
- 附录说明：搜索"附录"、"规范性"、"资料性"等关键词

判断内容完整性：
- 必备内容是否齐全
- 表述是否规范
- 顺序是否合理

生成问题列表：
- 缺失内容 → ERROR
- 表述不规范 → WARNING
- 可优化内容 → SUGGESTION
```

#### 3.2 范围内容审查

**审查内容**：

1. **适用范围描述**
   - 检查是否清晰界定适用范围
   - 检查是否使用规范表述："本文件规定了..."
   - 检查适用领域是否明确

2. **不适用情况**
   - 检查是否明确不适用情况（如有）
   - 格式示例："本文件不适用于..."

3. **表述准确性**
   - 检查范围描述是否准确
   - 检查是否与后续内容一致

**AI判断逻辑**：

```
读取范围章节内容

分析：
- 是否使用"本文件规定了..."标准表述
- 是否说明适用领域和对象
- 是否说明不适用情况（如有）

判断：
- 范围描述是否清晰
- 是否与后续内容一致
- 是否存在遗漏或多余内容

生成建议：
- 表述不清晰 → WARNING
- 缺少必要内容 → ERROR
- 可优化表述 → SUGGESTION
```

#### 3.3 条款类型判断

**审查内容**：

1. **要求型条款**
   - 使用"应"、"应该"
   - 判断是否为强制性要求
   - 检查表述是否恰当

2. **推荐型条款**
   - 使用"宜"、"建议"
   - 判断是否为推荐性建议
   - 检查表述是否恰当

3. **陈述型条款**
   - 使用"可"、"能"
   - 判断是否为允许性陈述
   - 检查表述是否恰当

**AI判断逻辑**：

```
扫描包含能愿动词的条款

分析条款内容：
- 要求型：必须执行的要求 → 应使用"应"
- 推荐型：建议执行的内容 → 应使用"宜"
- 允许型：允许但不强制 → 应使用"可"

判断：
- 条款类型与表述是否匹配
- 是否存在表述不当的情况

生成问题：
- 类型不匹配 → ERROR
- 表述不当 → WARNING
```

#### 3.4 术语和定义审查

**审查内容**：

1. **定义准确性**
   - 检查定义是否清晰、完整
   - 检查是否与国家标准一致
   - 检查是否引用标准定义

2. **术语使用一致性**
   - 检查同一概念是否使用统一术语
   - 检查是否在首次出现时定义

3. **格式规范**
   - 检查术语首次出现是否加粗
   - 检查缩略语是否标注全称

**AI判断逻辑**：

```
读取术语和定义章节

检查：
- 每个术语是否有清晰定义
- 定义是否引用标准
- 是否存在未定义即使用的情况

全文扫描：
- 同一概念是否使用不同术语
- 术语首次出现是否加粗
- 缩略语是否标注全称

生成问题：
- 定义不清晰 → WARNING
- 术语不一致 → ERROR
- 格式不规范 → WARNING
```

#### 3.5 规范性引用文件审查

**审查内容**：

1. **引用标准版本**
   - 检查引用标准是否为最新版本
   - 注意：AI无法实时查询，需提示用户确认

2. **引用格式**
   - 检查是否区分注日期引用和不注日期引用
   - 检查引用格式是否规范

3. **引用顺序**
   - 检查引用文件排列顺序
   - 国家标准、行业标准、国际标准等

**AI判断逻辑**：

```
读取规范性引用文件章节

检查：
- 引用标准编号和年份
- 引用格式是否规范
- 排列顺序是否合理

提示：
- 无法确认是否为最新版本，需用户确认
- 建议查询最新版本

生成问题：
- 引用格式错误 → ERROR
- 顺序不合理 → WARNING
- 版本可能过期 → SUGGESTION
```

#### 3.6 内容一致性审查

**审查内容**：

1. **术语一致性**
   - 同一概念是否使用统一术语
   - 是否存在同义词混用

2. **内容匹配**
   - 章节内容是否与标题匹配
   - 引用内容是否存在

3. **数据一致性**
   - 数据是否前后一致
   - 图表编号是否与正文引用一致

**AI判断逻辑**：

```
全文扫描

检查：
- 术语使用是否一致
- 章节内容是否偏离标题
- 引用的章节/图表是否存在
- 数据是否前后一致

生成问题：
- 内容不匹配 → ERROR
- 数据不一致 → ERROR
- 术语不一致 → WARNING
```

### 步骤4：生成综合报告

**汇总结果**：
- 脚本检查结果（格式、规则）
- AI审查结果（语义、内容）

**生成报告**：
- 按严重等级分类
- 标注问题来源（脚本/AI）
- 提供详细修改建议

## AI 审查能力边界

### AI能够有效识别

- ✅ 语义层面的问题
- ✅ 内容完整性问题
- ✅ 表述清晰度问题
- ✅ 逻辑一致性问题
- ✅ 格式规范问题

### AI需要用户确认

- ⚠️ 引用标准是否为最新版本
- ⚠️ 专业术语的准确性
- ⚠️ 技术内容的正确性
- ⚠️ 与行业标准的符合性

### AI无法替代

- ❌ 专业审查人员的判断
- ❌ 法律法规符合性审查
- ❌ 特殊格式要求的专业判断

## AI 审查建议生成原则

### 1. 基于标准

所有建议应基于 GB/T 1.1-2020 标准。

### 2. 具体可行

建议应具体、可操作，避免模糊表述。

### 3. 提供示例

对于复杂问题，提供修改示例。

### 4. 说明理由

说明为什么这是个问题，帮助用户理解。

## 审查报告格式

### 问题编号规则

- **S系列**：结构问题（Structure）
- **F系列**：格式问题（Format）
- **T系列**：术语问题（Terminology）
- **AI系列**：AI发现的问题

### 严重等级

- **ERROR**：必须修改
- **WARNING**：建议修改
- **SUGGESTION**：可选修改

### 来源标注

- **脚本**：由自动化脚本发现
- **AI**：由AI深度分析发现

## 注意事项

### 1. 避免过度审查

AI应关注重要问题，避免报告过多细节问题。

### 2. 尊重专业判断

AI应明确说明审查结果仅供参考。

### 3. 提供清晰建议

建议应清晰、具体、可操作。

### 4. 适应不同类型标准

AI应能适应国家标准、行业标准、企业标准等不同类型。
